# This is the exact table every real USB keyboard is translated through by the
# Linux HID core: hid-input.c uses `hid_keyboard[usage->hid & HID_USAGE]` to map
# an incoming HID usage straight to a KEY_* code before injecting the input
# event. It is canonical for the uinput backend for exactly that reason -- it is
# not an independent implementation of the mapping, it *is* the mapping the
# kernel ships.
#
# Format: one row per usage, tab-separated:
#   <usage hex>	<KEY_* name>	<evdev numeric code>
#
# Full 0x00-0xFF range of the array is listed, not just the printable/letter
# keys, per the task brief. KEY_RESERVED (code 0) at 0x00-0x03 reflects that HID
# defines those four usages as status conditions (no-event, ErrorRollOver,
# POSTFail, ErrorUndefined), not physical keys -- consistent with
# docs/PROTOCOL.md §6.15's own reservation of usages 0x00-0x03 in the KEYBOARD
# message's `keys[]` bitmap. KEY_UNKNOWN (code 240) marks a slot the kernel
# array itself leaves unmapped (`unk` in the source); it is not this file
# inventing a fallback -- it is what the kernel does.
#
# One evdev value, KEY_DELETE (111), appears at THREE indices in the source
# array -- 0x4C ("Delete Forward"), 0x9C, and 0xD8, both of the latter two
# being HID-reserved indices in the 0x82-0xDF gap that the kernel
# nonetheless assigns; see the data rows below for all three. That is the
# kernel array's own choice, reproduced faithfully rather than "corrected".
# (Corrected 2026-08-25: this comment previously said "0x9C appears twice",
# citing only 0x4C and 0x9C and omitting 0xD8 -- the data rows were always
# right, only this prose was stale. See references/hid/README.md for the
# note on the correction.)
#
# No value in this file was inferred, guessed, or filled in from memory --
# every row is a direct transcription of hid_keyboard[usage] followed by a
# direct lookup of that numeric value's #define name in input-event-codes.h at
# the same pinned tag. Where hid_keyboard[] and #define KEY_UNKNOWN disagreed
# with the author's own recollection at any point during extraction, the
# fetched source files won, per the blind-platform rule in docs/CONVENTIONS.md --
# recollection was not used to fill anything here.
